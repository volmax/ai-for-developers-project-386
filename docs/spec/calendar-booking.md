# Система бронирования календаря

## Формулировка проблемы

Владельцу календаря нужно простое решение для управления доступными типами событий и просмотра предстоящих встреч. Гостям нужно возможность записаться на событие без регистрации — выбрать тип, открыть календарь, выбрать свободный слот и забронировать его.

## Решение

Сервис бронирования с двумя ролями:
- **Владелец календаря** — просматривает предстоящие встречи, типы событий захардкожены.
- **Гость** — выбирает тип события, открывает календарь на 14 дней вперёд, выбирает свободный слот и создаёт бронирование без регистрации.

## Пользовательские сценарии

1. Как **владелец календаря**, я хочу видеть список предстоящих встреч (сегодня + будущее), чтобы контролировать свой график.
2. Как **гость**, я хочу видеть доступные типы событий с названием, описанием и длительностью, чтобы выбрать что забронировать.
3. Как **гость**, я хочу выбрать тип события и увидеть календарь доступных слотов на 14 дней вперёд, чтобы подобрать удобное время.
4. Как **гость**, я хочу создать бронирование на свободный слот, чтобы встреча была зарезервирована.
5. Как **гость**, я хочу получить понятное сообщение об ошибке, если пытаюсь занять уже занятое время, чтобы выбрать другой слот.
6. Как **гость**, я хочу быть защищённым от случайного двойного бронирования при двойном клике, чтобы не забронировать дважды.
7. Как **владелец календаря**, я хочу, чтобы система предотвращала пересечение бронирований даже для разных типов событий, чтобы мой график оставался корректным.
8. Как **гость**, я хочу указать имя (и опционально email) при бронировании, чтобы владелец мог меня идентифицировать.
9. Как **владелец календаря**, я хочу, чтобы окно записи начиналось с завтрашнего дня, чтобы не получать спонтанных бронирований на сегодня.
10. Как **гость**, я хочу видеть слоты только в рабочие часы владельца (09:00–18:00), чтобы не бронировать вне рабочего времени.
11. Как **владелец календаря**, я хочу, чтобы система корректно обрабатывала конкурентные запросы на бронирование, чтобы два гостя не заняли один слот.
12. Как **гость**, я хочу видеть подтверждение на экране после успешного бронирования, чтобы знать, что встреча зарезервирована.

## Решения по реализации

### Архитектурные решения

- **Бэкенд**: Spring Boot 4.1.2, Java 21, база данных H2, springdoc-openapi (Swagger UI).
- **Фронтенд**: React 19, Vite 6, TypeScript 5, Tailwind CSS 3, react-router-dom v7.
- **Стиль API**: REST, ресурсные эндпоинты в `/api/`.
- **Часовой пояс**: жёстко задан `Europe/Moscow` для всех расчётов слотов и отображения.

### Предметная модель

- **EventType** — фиксированный тип события, определённый в коде. Два варианта: 15 минут и 30 минут. Каждый тип имеет id, name, description и durationMinutes. CRUD отсутствует — типы определены в коде.
- **Booking** — бронирование слота гостем. Содержит: guestName (обязательно), guestEmail (опционально), eventTypeId, eventTypeName (денормализовано), eventDurationMinutes (денормализовано), slotStart, slotEnd, createdAt.
- **BookingWindow** — 14 календарных дней, начиная с завтрашнего дня (не включая сегодня). Гость может бронировать только в пределах этого окна.
- **Owner** — владелец календаря, профиль задаётся через `application.properties` (имя, email).

### Модель данных

**Одна таблица `Booking`** — слоты вычисляются динамически, не предгенерируются.

| Столбец | Тип | Примечание |
|---------|-----|------------|
| id | BIGINT (PK, auto) | Первичный ключ |
| event_type_id | VARCHAR | Ссылка на тип события |
| event_type_name | VARCHAR | Денормализовано для отображения |
| event_type_duration_minutes | INT | Денормализовано для расчёта слотов |
| slot_start | TIMESTAMP | Время начала бронирования |
| slot_end | TIMESTAMP | Время окончания бронирования |
| guest_name | VARCHAR | Обязательно |
| guest_email | VARCHAR | Опционально |
| created_at | TIMESTAMP | Автоматически при создании |

**Уникальное ограничение**: `(slot_start, event_type_id)` — предотвращает двойное бронирование одного слота одного типа.

**Обнаружение конфликтов**: при создании бронирования проверяется, что предлагаемый интервал `[slot_start, slot_end]` не пересекается с любым существующим бронированием. Пересечение = два интервала пересекаются в какой-то точке (например, 10:00–11:00 пересекается с 10:30–11:00, но не пересекается с 11:00–12:00).

### Контракты API

#### Типы событий

```
GET /api/event-types
Ответ: EventType[]
{
  id: string,
  name: string,
  description: string,
  durationMinutes: number  // 15 или 30
}
```

#### Бронирования

```
POST /api/bookings
Запрос: {
  eventTypeId: string,
  slotStart: string (ISO 8601),
  guestName: string,
  guestEmail: string?
}
Ответ: Booking (201) или ошибка (409 при конфликте)

GET /api/bookings/upcoming
Ответ: Booking[] — только сегодняшние и будущие бронирования

GET /api/bookings/available-slots?eventTypeId=string&date=string (ISO 8601)
Ответ: string[] — список доступных времен начала слотов в формате ISO 8601

GET /api/bookings/free-slots-count?eventTypeId=string&date=string (ISO 8601)
Ответ: number — количество свободных слотов на заданную дату
```

### Design First: TypeSpec

Используем подход **Design First** с TypeSpec как единым источником истины для API-контракта.

#### Инструменты

- **TypeSpec** — язык спецификаций API от Microsoft. Компилируется в OpenAPI 3.0.
- **OpenAPI 3.0** — генерируемый формат, используемый как контракт.
- **springdoc-openapi** — Spring Boot интеграция, использует OpenAPI для Swagger UI.
- **openapi-typescript** — генерация TypeScript-клиента из OpenAPI для фронтенда.
- **TypeSpec CLI** (`tsp`) — компиляция TypeSpec в OpenAPI.

#### Структура проекта

```
typespec/
├── main.tsp              — вся спецификация (один файл, простота)
├── tspconfig.yaml        — конфигурация TypeSpec (генерация OpenAPI)
└── package.json          — зависимости TypeSpec
```

#### Организация

- **Namespace**: `Calendar`
- **Один файл**: `main.tsp` — все модели и операции в одном месте (масштаб проекта позволяет).
- **Модели**: `EventType`, `Booking`, `ErrorResponse`.
- **Операции**: CRUD для бронирований, получение типов событий, расчёт слотов.

#### Генерация

- **Из TypeSpec → OpenAPI 3.0**: `tsp compile main.tsp --emit @typespec/openapi3`
- **Из OpenAPI → TypeScript-клиент**: `openapi-typescript openapi.yaml -o frontend/src/types/api.ts`
- **Spring-код**: пишется вручную, но типы из сгенерированного OpenAPI используются как reference.

#### CI-проверка

Каждый коммит:
1. Генерирует OpenAPI из TypeSpec.
2. Генерирует TypeScript-клиент из OpenAPI.
3. Проверяет `git diff` — если сгенерированные файлы изменились, CI падает.
Это гарантирует, что контракт не рассинхронизировался с кодом.

#### Модели TypeSpec

```
model EventType {
  id: string;
  name: string;
  description: string;
  durationMinutes: int32;
}

model Booking {
  id: string;
  eventTypeId: string;
  eventTypeName: string;
  eventDurationMinutes: int32;
  slotStart: DateTime;
  slotEnd: DateTime;
  guestName: string;
  guestEmail: string;
  createdAt: DateTime;
}

model ErrorResponse {
  code: string;
  message: string;
}

model BookingRequest {
  eventTypeId: string;
  slotStart: DateTime;
  guestName: string;
  guestEmail?: string;
}
```

#### Валидация

- `guestName`: `minLength: 1` — обязательно.
- `guestEmail`: опционально, при наличии — валидация формата.
- `durationMinutes`: только 15 или 30.
- `slotStart`: в пределах BookingWindow (завтра + 14 дней), в рабочие часы (09:00–18:00).

#### Форматы

- **Дата/время**: `string` с форматом `date-time` (ISO 8601).
- **Ошибки**: единый формат `ErrorResponse { code: string, message: string }`.
- **Pagination**: нет в MVP.
- **Версионирование**: нет, пока `/api/`.

Для заданного типа события:
1. Определяем рабочие часы: 09:00–18:00 в `Europe/Moscow`.
2. Определяем шаг слота = длительность типа события (15 или 30 минут).
3. Генерируем кандидаты: 09:00, 09:15/09:30, 09:30/09:45, ... до 18:00.
4. Для каждого кандидата проверяем, не пересекается ли `[candidate_start, candidate_start + duration]` с любым существующим бронированием (независимо от типа).
5. Возвращаем только свободные слоты.

### UI спецификация

#### Header (общий для всех страниц)

- Логотип: оранжевая иконка календаря + текст "Calendar" (ссылка на `/`)
- Навигация: "Записаться" (ссылка на `/events`), "Админка" (ссылка на `/admin/meetings`)

#### Главная страница (`/`)

- **Левая колонка:**
  - Бейдж: "БЫСТРАЯ ЗАПИСЬ НА ЗВОНОК"
  - Заголовок: "Calendar"
  - Описание: "Забронируйте встречу за минуту: выберите тип события и удобное время."
  - Кнопка: "Записаться" (оранжевая, ссылка на `/events`)
- **Правая колонка:**
  - Карточка "Возможности" с тремя пунктами:
    - Выбор типа события и удобного времени для встречи
    - Быстрое бронирование с подтверждением и дополнительными заметками
    - Управление типами встреч и просмотр предстоящих записей в админке

#### Каталог событий (`/events`)

- Заголовок: "Выберите тип события"
- Подзаголовок: "Нажмите на карточку, чтобы открыть календарь и выбрать удобный слот"
- Карточки событий (две):
  - "Встреча 15 минут" (бейдж "15 мин") — "Короткий тип события для быстрого слота"
  - "Встреча 30 минут" (бейдж "30 мин") — "Базовый тип события для бронирования"
- Клик на карточку → переход на `/booking/:eventTypeId`

#### Страница бронирования (`/booking/:eventTypeId`)

- **Три колонки:**
  1. **Инфо о событии (левая):**
     - Аватар/имя хоста (например, "Tota" + подпись "Host")
     - Название события (например, "Встреча 15 минут" с бейджем длительности)
     - Описание события
     - Блок "Выбранная дата" — текстовое представление (например, "вторник, 31 марта")
     - Блок "Выбранное время" — "Время не выбрано" или выбранный слот
  2. **Календарь (центральная):**
     - Заголовок "Календарь"
     - Навигация по месяцам: кнопки ← → и название месяца с годом (например, "март 2026 г.")
     - Календарная сетка: дни недели (Пн, Вт, Ср, Чт, Пт, Сб, Вс), числовые ячейки
     - Каждая ячейка дня показывает: число + количество свободных слотов (например, "31 33 св.")
     - Неактивные дни (за пределами 14-дневного окна) — приглушённый стиль
  3. **Статус слотов (правая):**
     - Заголовок "Статус слотов"
     - Список слотов для выбранной даты с временем и статусом:
       - Свободные: белый фон, текст "Свободно"
       - Занятые: серый фон, текст "Занято"
     - Кнопки: "Назад" (возврат к каталогу), "Продолжить" (переход к форме бронирования)

#### Страница админки (`/admin/meetings`)

- Предстоящие встречи (сегодня + будущее)
- Отображение: тип события, гость (имя, email), время начала/окончания

### Тестирование

#### Что считать хорошим тестом

- Тестировать только внешнее поведение — ответы API, рендеринг фронтенда, взаимодействия пользователя.
- Не тестировать детали реализации — внутренние методы, приватные поля, фреймворковые детали.
- Тестировать обнаружение конфликтов на конкретных сценариях (пересекающиеся интервалы, соседние интервалы, одно время разные типы).
- Тестировать расчёт слотов на граничных случаях (конец рабочих часов, конец 14-дневного окна).

#### Модули для тестирования

1. **REST API бэкенда** (интеграционные тесты) — все эндпоинты: типы событий, создание бронирования, предстоящие встречи, доступные слоты, количество свободных слотов.
2. **Сервисный слой бэкенда** (unit-тесты) — логика расчёта слотов, обнаружение конфликтов, проверка окна записи.
3. **Компоненты фронтенда** (компонентные тесты) — существующий паттерн Vitest + Testing Library + `userEvent` (см. `__tests__/components/button.test.tsx`). Новые страницы: EventTypesPage, BookingPage, AdminMeetingsPage.
4. **API-клиент фронтенда** (unit-тесты) — обработка запросов/ответов, маппинг ошибок.

#### Предыдущий опыт

- Существующие тесты используют Vitest + Testing Library + `userEvent` (см. `__tests__/components/button.test.tsx`).
- Бэкенд использует Spring Boot test (spring-boot-starter-test уже в pom.xml).

## Вне области видимости

- Аутентификация и регистрация для владельцев и гостей.
- Отмена бронирования любой стороной.
- Email-уведомления гостям.
- Управление профилем владельца через UI (имя/email задаются в конфиге).
- Мульти-таймзонная поддержка.
- Периодические (повторяющиеся) бронирования.
- Аналитика и отчёты для владельца.
- Предгенерированные таблицы слотов в базе данных.
- Редактирование бронирования.

## Дополнительные заметки

- Окно записи начинается **с завтрашнего дня** (не сегодня) и занимает **14 календарных дней**.
- Шаг слота равен **длительности конкретного типа события** (15 или 30 минут), а не глобальному шагу.
- Обнаружение пересечений **глобальное**: бронирования разных типов событий не могут пересекаться по времени.
- Система использует **пессимистическую блокировку** на уровне базы данных для обработки конкурентных запросов.
- Типы событий **захардкожены** — CRUD для владельца не реализован.
- На странице бронирования календарь показывает количество свободных слотов на каждый день.
- Слоты отображаются в правой колонке с визуальным статусом (занято/свободно).
